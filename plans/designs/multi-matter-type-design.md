## Problem Statement

CaseFor AI is an EB-1A visa case builder. Its pipeline (extraction, analysis, drafting, strength evaluation, denial probability) is hardcoded to EB-1A's 10 criteria across ~15 files. A key eng+product stakeholder requires it to support multiple immigration matter types (O-1B, O-1A, EB-2 NIW, etc.) configurable through admin UI by a lawyer, not an engineer. The acceptance criterion is a full pipeline demo: O-1B running end-to-end with criteria, templates, prompts, and rubrics all admin-configured.

## Demand Evidence

- Specific request from key eng+product leader (not a single client ask)
- Every competitor (Docketwise, Litify, LollyLaw, Imagility, eimmigration) supports multi-visa natively. This is table stakes for credibility.
- 4 users in the current system, all on EB-1A. No paying customers yet.
- Demo bar: full pipeline for O-1B, all admin-configured

## Status Quo

Today, adding a second matter type requires an engineer to:
1. Add new criterion IDs to `CriterionIdSchema` enum in `eb1a-extraction-schema.ts`
2. Write Zod schemas per criterion in `criterion-extraction-schemas.ts`
3. Add prompt slug mappings in `multipass-extraction.ts` (`ANALYSIS_SLUGS`)
4. Write a strength evaluation rubric (300+ line prompt) in `strength-evaluation.ts`
5. Update document classifier categories
6. Modify denial probability framework for the new legal standard
7. Seed criteria, templates, and prompts in the DB

That's ~3-5 days of engineering per matter type. The stakeholder wants it to be a 30-minute admin operation.

## Constraints

- Next.js 16 + Prisma 7 + PostgreSQL (Supabase) + Claude Sonnet + Pinecone RAG. No stack changes.
- Existing data model (ApplicationType, CriteriaMapping, Template, AgentPrompt) is the right foundation. Extend, don't replace.
- "Lawyer configurable" = define criteria names/descriptions, select/write prompt templates, set thresholds via admin UI. No code, no Zod schemas, no pipeline work.
- Pipeline supports the "criteria + evidence types + strength rubric" constrained pattern, not arbitrary evaluation frameworks.
- O-1B is the right second type for demo (8 criteria, significant overlap with EB-1A's 10).
- Tier 3 entities (intake form schema, case lifecycle, report panel phases, per-evidence extraction schemas) are deferred.

## Premises

1. Extend existing data model, don't replace.
2. Admin UI needs significant new work alongside pipeline refactor (both are critical).
3. "Lawyer configurable" = no code, no schemas, no pipelines.
4. Pipeline supports constrained "criteria + evidence types + rubric" pattern (revised from "arbitrary" per Codex challenge).
5. O-1B is the demo target (criteria overlap reduces blast radius).

## Approaches Considered

### Approach A: Pipeline First (CHOSEN)
Refactor all ~15 hardcoded pipeline files to read from DB-driven config. Build minimal admin UI for new entities (rubrics, evidence types, criterion-prompt links). Seed O-1B via script or minimal wizard.

- Effort: L
- Risk: Medium (regression across analysis pipeline)
- Pros: Pipeline becomes truly dynamic; every future type is free; clean separation between config and execution
- Cons: Large blast radius (15+ files); lawyer self-service requires admin UX to follow

### Approach B: Admin First
Build admin UX flows first (wizard, cloning, rubric editor), then refactor pipeline to read from admin-produced config.

- Effort: L
- Risk: Low (admin is additive)
- Pros: Validates data model before pipeline changes; lower regression risk
- Cons: Full demo requires both phases; admin without pipeline is show-don't-tell

### Approach C: Clone + Override
Clone pipeline files per matter type (o1b-agent.ts, etc.). No generalization.

- Effort: M per type (linear growth)
- Risk: High (code duplication, maintenance)
- Cons: Contradicts "lawyer configurable" requirement. Rejected.

## Recommended Approach

**Approach A: Pipeline First.** The user (the builder) chose this because:
1. The pipeline refactor is the hardest, riskiest work. Do it while you have full context.
2. The demo is "O-1B running end-to-end" -- that requires a working pipeline, not a polished wizard.
3. Admin UX can be rough for the demo; pipeline can't be.

## Implementation Plan

### Phase 1: Data Model Extensions

New/modified Prisma models:

**Extend AgentPrompt:** Add optional `applicationTypeId` FK so prompts can be scoped per type.

```prisma
model AgentPrompt {
  // existing fields...
  applicationTypeId String?
  applicationType   ApplicationType? @relation(...)
}
```

Lookup priority: type-specific prompt -> global prompt -> hardcoded fallback.

**New: EvidenceTypeDefinition**

```prisma
model EvidenceTypeDefinition {
  id                String   @id @default(cuid())
  applicationTypeId String
  key               String   // e.g., "publications", "awards"
  name              String
  description       String?
  fields            Json     // [{key, label, type}] -- schema for evidence items
  defaultCriteria   String[] // criterion keys this evidence maps to by default
  displayOrder      Int      @default(0)
  active            Boolean  @default(true)

  applicationType ApplicationType @relation(...)
  @@unique([applicationTypeId, key])
}
```

**New: StrengthRubric**

```prisma
model StrengthRubric {
  id                String  @id @default(cuid())
  applicationTypeId String  @unique
  content           String  // The full rubric prompt (text, not structured)
  version           Int     @default(1)
  updatedAt         DateTime @updatedAt

  applicationType ApplicationType @relation(...)
}
```

**New: CriterionPromptLink**

```prisma
model CriterionPromptLink {
  id                String @id @default(cuid())
  applicationTypeId String
  criterionKey      String
  promptSlug        String // links to AgentPrompt.slug
  purpose           String @default("analysis") // "analysis", "drafting", "evaluation"

  applicationType ApplicationType @relation(...)
  @@unique([applicationTypeId, criterionKey, purpose])
}
```

**New: DocumentCategoryMapping** *(optional for demo -- O-1B shares most categories with EB-1A)*

```prisma
model DocumentCategoryMapping {
  id                String @id @default(cuid())
  applicationTypeId String
  category          DocumentCategory
  active            Boolean @default(true)

  applicationType ApplicationType @relation(...)
  @@unique([applicationTypeId, category])
}
```

**New: DenialFramework** *(optional for initial demo -- denial probability can fall back to EB-1A framework for O-1B initially)*

```prisma
model DenialFramework {
  id                String @id @default(cuid())
  applicationTypeId String @unique
  frameworkName      String // "Kazarian Two-Step", "Dhanasar Three-Prong", etc.
  content           String // The full framework prompt
  version           Int    @default(1)
  updatedAt         DateTime @updatedAt

  applicationType ApplicationType @relation(...)
}
```

### Phase 2: Pipeline Dynamism (the big refactor)

File-by-file refactor plan. Each file gets one change: replace hardcoded config with a dynamic lookup.

Blast radius: ~16 lib pipeline files + ~16 front-end/API consumers of extraction types = **~32 files total**. The lib files are the structural changes; the front-end files are import/type updates.

|---|---|---|

## Reviewer-Identified Gaps (fixed in this revision)

### Gap 1: EB1AAnalysis model not addressed

The Prisma `EB1AAnalysis` model is named EB-1A-specifically and referenced throughout. **Decision:** Rename to `CaseAnalysis` with an `applicationTypeId` FK during the refactor. The `strongCount`/`weakCount`/`criteria` JSON fields are generic enough to work for any criteria-based matter type. Add to Phase 2 refactor table. **Migration:** FK is nullable; backfill existing rows with the EB-1A `ApplicationType.id` via a seed script before the rename. Use `prisma db push` (not `migrate dev`, per project convention).

### Gap 2: CriterionId TypeScript type and CRITERIA_METADATA

`CriterionId` is a compile-time union type (`"C1" | "C2" | ... | "C10"`), and `CRITERIA_METADATA` is a static `Record<CriterionId, {...}>`. These can't be "dynamic" at the TypeScript level. **Decision:** Replace `CriterionId` type with `string` throughout. Replace `CRITERIA_METADATA` constant with a `getCriteriaMetadata(applicationTypeId): Promise<Record<string, CriterionMeta>>` function that reads from CriteriaMapping. TypeScript loses compile-time exhaustiveness checks on criterion IDs, but gains runtime flexibility. This is the correct tradeoff for a configurable system.

### Gap 3: Rollback strategy

The hardcoded fallback chain (`type-specific prompt -> global prompt -> hardcoded EB-1A fallback`) IS the rollback strategy. During migration: keep hardcoded fallbacks alive. If a type-specific config is missing or broken, the pipeline falls back to the global/hardcoded version. After O-1B is verified working, the hardcoded fallbacks can be removed (or kept as the EB-1A type-specific config). No feature flags needed; the lookup chain is the flag.

### Gap 4: AgentPrompt.applicationTypeId vs CriterionPromptLink

Division of responsibility: `CriterionPromptLink` handles **per-criterion** prompts (extraction analysis, evidence verification -- "how do I evaluate criterion X?"). `AgentPrompt.applicationTypeId` handles **agent-level** prompts (drafting agent system prompt, document agent system prompt, strategy agent -- "how does this agent behave for this matter type?"). These are different scopes. A criterion has many prompts; an agent has one system prompt per type.

### Gap 5: EvidenceTypeDefinition.fields -> dynamic Zod schema (highest-risk bet)

This is the hardest technical decision. Three options:

**Option A: Fully dynamic.** Build Zod schemas from `fields` JSON at runtime. Pro: lawyer can define any evidence type. Con: no TypeScript inference, runtime schema errors, potential `generateObject` edge cases with AI SDK.

**Option B: Schema registry.** Keep rich per-category schemas (PublicationSchema, AwardSchema, etc.) as code. Admin config selects WHICH schemas a matter type uses and maps them to criteria. Pro: compile-time safety, tested schemas. Con: adding a truly novel evidence type requires code.

**Option C: Hybrid (CHOSEN).** Ship a set of ~15 "common evidence type templates" as code (publications, awards, patents, memberships, media, judging, speaking, grants, leadership, compensation, exhibitions, commercial, original contributions, certifications, recommendations). Admin selects from this registry and maps to criteria. If a type needs a novel evidence type not in the registry, an engineer adds a new template (5 min, one file). This covers 95% of immigration matter types without runtime schema generation.

**Prototype gate:** Before committing, test `generateObject` with a dynamically constructed Zod schema in a throwaway script. If it works cleanly, upgrade to Option A later.

### Gap 6: DocumentCategory enum

**Decision:** Migrate `DocumentCategory` from Prisma enum to `String` field during this refactor. This is a one-time breaking change best done now alongside the other schema changes. Existing enum values become seed data in `DocumentCategoryMapping`. New types can define arbitrary categories.

## Open Questions

1. **Criterion key format:** Use type-prefixed keys (`EB1A-C1`, `O1B-C1`) for global uniqueness, or rely on `(applicationTypeId, criterionKey)` composite uniqueness from CriteriaMapping? Composite is cleaner but requires always carrying the type context.
2. **Prompt versioning per type:** Should CriterionPromptLink pin to a specific prompt version, or always use the latest?
3. **Intake form:** Deferred, but worth thinking about: does the intake form need to be per-type, or can a generic "tell us about yourself" intake work for all immigration types?

## Success Criteria

1. O-1B case runs through the full pipeline (extraction, analysis, strength eval, drafting, denial probability) using admin-configured criteria, prompts, and rubrics -- no code changes required per type.
2. A non-engineer can create a new matter type through admin UI (clone + modify flow) in under 30 minutes.
3. EB-1A continues to work identically after the refactor (zero regression).
4. Adding a third type (e.g., EB-2 NIW) requires only admin configuration, not code.
